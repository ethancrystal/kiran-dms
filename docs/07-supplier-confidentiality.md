# 07 — Supplier Confidentiality (the "Classified Supplier")

**Rule:** the supplier's identity, contact details, pricing, terms, lot/reference numbers and documents are visible to the **owner** and to anyone the owner has explicitly **granted** vault access (by default: the manager). Nobody else — not reps, not a future accountant, not a developer looking at production data — can see them, and the database, not the user interface, enforces it.

Why it matters commercially: in distribution, the supplier relationship *is* the business. A rep or manager who learns where the stock comes from and at what price can cut Kiran out of the chain, or sell that information to a competitor. The vault design treats this as the single most valuable secret in the system.

## 1. What is classified

| Classified (vault only) | Public to the business (normal RLS) |
|---|---|
| Supplier legal and trade name, country, addresses | Kiran's own product labels (`product.brand_label`), product names, SKUs, selling prices |
| Supplier contacts (people, phones, emails, WhatsApp) | Stock quantities by location |
| Purchase prices, cost snapshots, landed cost, margin | Batch codes **as Kiran assigns them** and expiry dates |
| Payment terms, credit terms, MOQ, lead times | Reorder points and restock suggestions **in units**, without cost |
| Purchase orders, goods receipts, supplier invoices, contracts, shipping documents | That a stock receipt happened, date, SKU, qty, opaque receipt reference |
| Supplier lot/reference numbers | — |
| Bank details used to pay the supplier, and the bank lines that pay them | Kiran's customer-facing bank accounts |

## 2. Data design

- **Separate schema `vault`** (implemented as `supplier_vault`, because Supabase reserves `vault`; doc 12 D-13) — not added to PostgREST's exposed schemas, so there is no REST surface at all. The only access is through `SECURITY DEFINER` functions in schema `vault_api` that check `app.has_vault_grant(auth.uid())` **and** `aal2` before returning anything.
- **The only link** between `vault` and `public` is `sku_id` on `purchase_order_line` / `goods_receipt` lines. There is **no** `supplier_id` on `product` or `sku`, no "manufacturer" field, no free-text that invites someone to type the name. `product.brand_label` holds Kiran's chosen public label.
- **Column encryption** for identity and cost fields (`*_enc`) using `pgsodium` with a key stored in Supabase Vault — so even a database dump or a misconfigured policy yields ciphertext. Decryption happens inside the grantee-checked functions only.
- **Goods receipt bridge.** When a vault goods receipt is posted, `vault_api.post_goods_receipt()` writes a `public.stock_movement(kind='receipt')` carrying only `sku_id`, `qty`, Kiran's `batch_id`, and an opaque `source_id`. Nothing in `public` can be joined back to a supplier.
- **Cost for margin reports** comes from `vault.cost_snapshot` through `vault_api.margin_by_sku()` — a function, not a view — so it is impossible to accidentally expose cost through a reporting view.
- **Vault access log** (`vault.vault_access_log`) records every function call: who, when, which records, and a required `purpose` string (e.g., "monthly restock planning"). It appears in the owner's daily digest.
- **Grants** are a boolean on `user_profile` that only the owner can set, with an audit event and an immediate effect. Revoking the manager's grant takes nothing else away.
- **Documents** (supplier invoices, contracts, shipping papers) live in a private bucket `vault-docs`; downloads are 5-minute signed URLs generated by a function that checks the grant; each download is logged; PDFs are watermarked with the viewer's name and time.
- **Backups** keep columns encrypted; the encryption key is backed up separately by the owner. Staging gets dummy vault rows, never real ones.

## 3. Leak vectors beyond the database — and the control for each

Software alone does not keep a supplier secret. These are the realistic ways it leaks, and what to do.

| Vector | Control |
|---|---|
| **Supplier name on cartons, delivery notes, shipping labels** when stock arrives | Stock is received by a vault grantee only; cartons are unpacked and relabelled (or shipping labels removed) before any rep sees them; a `goods_receipt` requires the receiver to confirm "labels removed". Consider a separate receiving address/time |
| **Product packaging itself** carries a manufacturer's name | If the supplier *is* the manufacturer and the pack names them, the identity is not secret from anyone who reads a bottle — only the commercial relationship and price are. If the supplier is a wholesaler/importer of a known brand, the brand is public but the source is not. **Open question OQ-04** decides whether private-label packaging is needed |
| **Invoices, receipts, statements sent to salons** | Templates render from `public` only; a rendering test asserts no vault field is reachable from the template context |
| **Bank statement import** — lines paying the supplier appear in the CSV | Pay the supplier from a **separate bank account** that is never imported; if that is impossible, the importer masks lines whose counterparty matches an owner-maintained "sensitive counterparties" list, and only grantees can see them |
| **Restock suggestions and PO drafting screens** | Suggestions in `public` show units and cover days only; the PO step happens in the vault UI |
| **WhatsApp groups, phone calls, office chatter** | Operational rule: the supplier is referred to as a codename (e.g., "Source A") everywhere outside the vault, including by the owner and manager; supplier calls are not taken on speaker in the office |
| **Error logs, analytics, support screenshots** | Vault screens excluded from session-replay/analytics; logs never include vault payloads; support requests redact |
| **Developer/contractor access** | Production vault data is ciphertext without the key; the key is not in developer environments; break-glass requires owner approval |
| **Exports** | No export function reads vault tables except an owner-only, watermarked "vault export" that exists for backup/audit purposes |
| **Accountant** | Receives sales/receipts/receivables/stock-at-cost **totals**; unit costs by SKU are released only if the owner decides to, via a vault export |
| **Former manager** | Grant revoked at offboarding; documents watermarked so any later leak is attributable |

## 4. Who gets a grant, and how

- Default at launch: **owner (implicit) + manager (granted)**.
- The grant is a conscious owner action, recorded, revocable in one tap, and visible on the user screen.
- A grantee's vault reads are reported in the owner's digest. Unusual patterns (reading all supplier contacts, bulk document downloads, reads outside working hours) are flagged by the anomaly job.
- If the owner later wants cost visibility without identity visibility (for example, to let an accountant see margins), the grant can be split into `vault_identity` and `vault_cost` — the schema is designed so this is a policy change, not a redesign.

## 5. Acceptance tests

1. With a rep token, every `vault_api` function returns `permission denied`; no vault table appears in the REST schema; `select * from vault.supplier` via the API is impossible.
2. With a manager token **without** grant, the same holds; with grant **and** AAL2, calls succeed and produce access-log rows.
3. A database dump opened without the key shows ciphertext in every `*_enc` column.
4. Rendering every customer-facing document template with a full fixture produces no string from the vault fixture.
5. The bank-statement importer masks sensitive counterparties for non-grantees.
6. Revoking the manager's grant takes effect on the next request.
