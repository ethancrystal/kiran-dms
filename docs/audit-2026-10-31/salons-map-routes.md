## Cross-cutting gaps

- No CRM frontend: `apps/web` has only login shells; there is no map, salon list, salon card, visit form, route screen, office territory/credit/route screens, or any RPC call to the salon/visit/route/order functions. Roadmap rows P1-03 (rep map) and P1-09 (offline PWA) are NOT STARTED.
- No offline layer or sync: PIP-07, MAP-02, DEM-01 all say "works offline"; no service worker, IndexedDB, outbox or `packages/shared` exists. The backend is ready for it only through client-generated ids and `client_id` idempotency.
- No unified salon timeline (SAL-05): visits, notes, stage events are three separate capped reads; orders, deliveries, payments, messages are not salon-history reads at all.
- Time-driven stage machine absent: nothing runs at_risk/dormant/blocked/parked-after-3-visits transitions (`cycle_missed`, `ageing`, `payment` triggers are enum values only), so MAP-01's colour set and PIP-06's "at-risk" are not backed by stage data. No scheduled job infrastructure found.
- Payments/installments (P1-07) not started: SAL-04 overdue status, exposure reduction, `collection_due` route stops and the PIP-09 handover condition all wait on it.
- No geometry: `area` has no boundary, so "geocoded to an area on sync" (MAP-02), "assigned to the territory they fall in" (MAP-07) and any map-based coverage have nothing to compute from. Pin is also not mandatory (B-30 PENDING).
- Excel import has no write path: the dry-run tool is the only artefact (SAL-10); real data run waits on MJ (B-02).
- Lost demand (DEM-02/03, roadmap P1-17) not started: the table, enums and `outcome`/`source` columns exist but nothing automatic writes them and there is no report. A failed delivery for lack of stock records nothing.
- Photos need storage (SAL-01, PIP-02, MAP-02): deferred by the rows themselves (L-0146, L-0152); no storage bucket or upload function exists.
- Test status unknown: no test was executed here, and `supabase/tests/crm-attacks.test.ts` (946 lines) is untracked, so it is not part of main; coverage claims above rest on titles only.

## Suspected defects

1. salons.sql:396-419 (`app.update_salon`), esp. 413-416: a rep may rewrite `lat`/`lng` of any salon in its territory with no restriction or flag. Visit and delivery distance (`distance_from_pin_m`, visits.sql:235-237; deliveries.sql:164-166) and the D-01 payment-distance control compare against that pin, so a rep can move the pin to where they stand and then log a "zero metres" visit. SAL-09 lets the rep edit, but doc 13 D-06 fake-visit detection assumes the pin is trustworthy.
2. (Needs an MJ decision, may be intended) orders.sql:309-326 (`app.office_set_blocked`) writes `salon_credit.blocked` only and never moves `salon.stage` to `blocked`, while `app.credit_of` (orders.sql:196) treats either as blocked. Doc 02 line 41 defines stage Blocked as automatic on ageing (not built), so there are two notions of blocked (manual credit hold vs ageing stage). MAP-01 colours pins by stage only, so a manually blocked salon will not show as blocked unless `office_override_stage` is also used.
3. visits.sql:116, 139, 173 (`my_open_day_id`, `rep_check_in`, `rep_check_out`): an open day is only "today" in Karachi time. A rep still working after midnight cannot log visits, orders or deliveries (no open day today), cannot check out (`rep_check_out` looks only at today, "no day to close"), and is blocked from checking in (earlier day open). Only the office force-close frees them. The error text at line 140 ("close it") is misleading because a rep has no function to close an earlier day.
4. salons.sql:379 (`create_salon`): `discovered_by` is set to the creator for every source, including `manual`, `referral`, `excel_import` and office-created rows, and the column is immutable (salon_guard line 183). MAP-07/CTL-13 define it as the discovering rep for the new-salon bonus; a bonus built on it would pay for imports and office entries.
5. salons.sql:363 (`create_salon` replay) compares only created_by, area and type: a replay with a different name, coordinates, phone or note silently returns the old row. `add_salon_note` (line 431) and `log_visit` do compare content, so this is inconsistent with the H-08 pattern.
6. inventory.sql:762-764 and salons.sql:593-595 (`record_demand` replay): the check compares sku, group, qty, reason but not `salon_id`; replaying a client_id with another salon returns the first row without error.
7. deliveries.sql:159-162 (`app.deliver`): insufficient stock raises an exception (rolling the transaction back) instead of recording a shortfall; even if DEM-02 capture were added at that point it would be rolled back with the failed delivery, so it needs a separate write path.
8. orders.sql:202-207 (`app.salon_exposure`): counts the full order total of `confirmed`, `partially_delivered` and `delivered` installment orders and has nothing that releases it, so each salon's exposure only grows toward its limit until payments exist (A-10 known). Also counts undelivered quantity of a part-delivered order.
9. routes.sql:184 (`app.due_list`): `limit 50` without paging or a count; for the office across all territories (or a rep with many due groups, one row per salon x group) rows beyond 50 are invisible, so some due/at-risk salons will never be listed.
10. salons.sql:72 and 414 (`name` nullable, `update_salon` sets it to null): name is optional "at first" (MAP-02) but nothing requires a name before the salon is ordered for, delivered to or invoiced.
11. visits.sql:3-6, 45-46 say "no field work without an open day", but `create_salon` (salons.sql:350), `add_salon_note` (422), `rep_add_stop` (234) and `record_demand` do not call `my_open_day_id`. Only visits, orders and deliveries are gated. PIP-09's text only demands the order gate, so this is a doc/code mismatch rather than a hard violation.
12. visits.sql:57 and 235: `visit.lat/lng` are NOT NULL but `log_visit` accepts null parameters and fails with a not-null violation (23502) rather than a clear 22023 refusal; GPS is required by PIP-02, so the failure mode is unfriendly rather than unsafe.
13. deliveries.sql:195-196: `basis_orders` increments per delivery, not per order, so a part-delivered order counts as several "orders" in the cycle estimate (affects any later PIP-05 estimation that trusts `basis_orders`).
14. No stage rule "Trial exits after 3 visits without order to Parked" (docs/02-growth-pipeline.md line 35) in `log_visit` (visits.sql:244-248): trial salons just accumulate visits.
