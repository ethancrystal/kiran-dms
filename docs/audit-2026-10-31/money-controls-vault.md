## Cross-cutting gaps

1. The whole payments domain is absent: no tables for installment, payment, receipt, cash ledger, handover or deposit (13 migrations, zero hits). It blocks PAY-01..05/07/10/11, CTL-01..04, 11, 15, 17, RPT-01/02 ageing. Roadmap item P1-07.
2. No messaging or Edge Function layer: no `supabase/functions`, no SMS/WhatsApp code. Receipts (CTL-01), OTPs (CTL-09, CTL-18), notices to old phone, reminders and digest delivery cannot exist.
3. No storage or photo handling anywhere (no bucket, no policy): blocks slip photos (PAY-02), deposit slips (CTL-04), adjustment photos (CTL-06), vault documents (VLT-05), rep photo (FLD-01), logo (ADM-02).
4. No digest, notification or reporting layer: CTL-15 and MSG-03 do not exist, so every "listed in the daily digest" clause (CTL-06, CTL-08, CTL-18) is unmet. Raw event sources exist (credit_event, approval_request, audit_event, duplicate_phones, stock_count).
5. Vault is an empty container: schemas locked and tested, `vault_api` has no functions, nothing calls `has_vault_grant`, and the audit chain cannot record reads (VLT-04 needs its own log). No key mechanism for CNIC or column encryption.
6. Config is seeded but unconsumed: `plan.templates`, `credit.rules`, `collections.escalation_days`, `payment.geofence_m`, `payment.max_minutes_after_arrival`, `cash.intraday_cap_paisa`, `office_cash.max_age_working_days`, `transfer.match_within_working_days` and the `approval.*` thresholds for payment_reversal, credit_note, restructure, purchase_order, petty_expense are read by no function. All are `[default-unconfirmed]`. `plan_code` is a hard enum, so PAY-01/ADM-01 "configurable templates" is not real.
7. Of the 12 `approval_kind` values only `discount` and `adjustment` have a consumer. `write_off`, `credit_note`, `payment_reversal`, `return_accept`, `restructure`, `credit_override`, `unblock`, `cancel_order`, `stage_override`, `device_approve` are enum values only (device approval uses `app.approve_device` directly). Owner-threshold routing lives inside each domain function (create_order for discounts, office_post_adjustment for adjustments), not in `request_approval` (which only forces `write_off` to the owner, foundation.sql:660).
8. The web app is login/MFA shells only (18 files, 2 RPCs, 1 table read). No requirement in this slice has a screen, so manager approvals, admin config, vault grant toggling, handover and dashboards are all unreachable for real users.
9. Credit exposure ignores payments by design for now (orders.sql:10-14, :202): it sums confirmed installment orders. It must be reworked in P1-07 or every salon that pays will stay "over limit".
10. Test coverage is strong for what exists (adjustments, issues, counts, discounts, credit caps, numbering, vault grant) but there are zero tests for anything payment, receipt, handover, digest, notification, vault-data or report, because none of that exists.

## Suspected defects

- supabase/migrations/20261028090000_orders.sql:202-207 `app.salon_exposure`: counts the full total of every delivered installment order forever, with no netting of payments. Correct only as a stand-in (comment at :13-14); a latent trap once payments land, since `evaluate_order` (:349) and `office_release_credit_hold` (:510) both use it.
- supabase/migrations/20261024223304_foundation.sql:654-660 `app.request_approval`: only `write_off` is routed to the owner. The seeded thresholds for `payment_reversal` (> Rs 10,000), `credit_note`, `restructure` (:789-792) are enforced nowhere, so a future reversal request created with the default checker role is decidable by a manager at any amount (docs/13 §9 requires owner above Rs 10,000).
- supabase/migrations/20261024223304_foundation.sql:615-633 `app.owner_set_config`: accepts any JSON for any key; no shape validation. A `plan.templates` whose percentages do not sum to 100, or a non-numeric `cash.intraday_cap_paisa`, would be accepted (the 100% check exists only as a test on the seed, foundation.test.ts "installment plan schedules each add up to 100%"). CTL-16 also asks for MFA re-authentication; `app.is_aal2()` is a session-level check, not a fresh re-auth.
- supabase/migrations/20261028060000_salons.sql:193-195 vs requirement CTL-09: the guard forbids every change of `verification_status` and no flow exists, so a salon can never become otp_verified/verified.
