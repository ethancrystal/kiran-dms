## 3. Suspected defects

Confidence is stated; none was reproduced because nothing was executed.

1. `supabase/config.toml:275-279` (and `jwt_expiry` L166): `[auth.sessions] timebox` and `inactivity_timeout` are commented out. SEC-04 (rep 14 days, office 12 h) is not enforced by anything in the repo. Refresh tokens rotate but never expire by time. High confidence for the local config; hosted settings could differ but are not in the repo.
2. `supabase/migrations/20261028060000_salons.sql:547-566` (`app.reveal_phone`): no count/time limit. A rep can page `my_salons` (50 per page, L501-515) and reveal every phone in its territory; each reveal is logged to `control.phone_reveal` but not blocked. This defeats the intent of SEC-06/SEC-07 (anti list-leak) except for after-the-fact review. High confidence.
3. `supabase/migrations/20261028080000_routes.sql:297-` (`app.my_route`) and `20261028050000_inventory.sql:783-801` (`my_bag`, `warehouse_availability`): rep list functions with no `limit`, unlike `my_salons`. SEC-07 page caps are inconsistent. Medium severity (bounded by data size today).
4. `supabase/config.toml:16`: comment states "the rep client additionally sends Range headers capped at 50 (H-14)". No client code does this (nothing under `apps/web` uses Range). The comment overstates the control; the real cap is only inside the specific functions plus `max_rows = 1000` (L19).
5. `apps/web/next.config.ts:10`: CSP is only `frame-ancestors 'none'`, with no `script-src`/`default-src`. Combined with `apps/web/lib/supabase/browser.ts:13-20` storing the raw device id (a bearer credential that the DB gate trusts via the `x-kiran-device` header) in localStorage, an XSS would let an attacker lift the approved-device credential. Medium; defence in depth missing for NFR-07.
6. `supabase/migrations/20261024223304_foundation.sql:529-546` (`owner_set_status`): disabling a user revokes devices but never touches `auth.sessions`/refresh tokens, and only the owner can call it (SEC-04/08 say O/Mg and "revoke sessions"). Data access is still cut because `app.user_role()` (L162-166) returns null for non-active users, so the practical risk is low; the gap is in the stated requirement and the missing one-click flow.
7. `supabase/migrations/20261025123056_device_revoked_final.sql` (`app.register_device`): any active user can insert unlimited `pending` device rows (only length of the id is checked; no per-user cap). Each row is also audited, so a rep script can grow `public.device` and `control.audit_event`. Low to medium (abuse by an authenticated user), and it also floods the approval list a manager must review.
8. `supabase/migrations/20261024223304_foundation.sql:319-320` (and the redefinition in `20261024232225_device_hardening.sql`): `control.audit_row()` locks the single `audit_chain_head` row for every audited write in the database, so all writes serialise. Fine for 10 reps, but it is an unmeasured ceiling and a lock-contention risk when offline outboxes sync in bursts (NFR-01/NFR-04).
9. `apps/web/e2e/rep-login.spec.ts:18-19`: test is titled as proving "NFR-01 rejection handling" but only checks a refused sign-in request surfaces an error. It does not exercise sync rejection. Also test 1 is labelled NFR-03 but only checks that one `lang="ur"` element exists. These titles overstate coverage.
10. `apps/web/proxy.ts:8`: comment still says "rep, phone OTP" although rep login is email code since L-0101 (stale). Cosmetic, listed because other docs were updated for L-0101.
11. `apps/web/app/layout.tsx:18`: `<html lang="en">` with no `dir`, no manifest link, no Urdu font loading; Urdu spans (`lang="ur"`) are not set `dir="rtl"`. NFR-03 "Nastaliq-safe" is not met by the shipped code.
12. `supabase/tests/helpers/db.ts:42-52` and `supabase/tests/setup/fixtures.ts:26`: RLS/AAL personas are simulated with forged `request.jwt.claims` (`aal`, `sub`) in a transaction, not real GoTrue sessions. The matrix proves the SQL logic only; the real MFA enrolment (`apps/web/app/office/mfa/page.tsx`) and aal2 claim production are not exercised by CI. Unverified assumption that Supabase mints `aal2` the way `app.is_aal2()` expects (L168-171).
13. Low confidence, not verified: `apps/web/app/office/mfa/page.tsx:27-37` enrols a TOTP factor for any signed-in AAL1 session that has no verified factor. If an office password were stolen before the owner's first enrolment, the thief could enrol their own factor. Whether the hosted Supabase project restricts this was not checked; the owner-bootstrap runbook enrols immediately, which narrows the window.
14. `supabase/config.toml:202`: `email_sent = 2` (per hour). If copied to a hosted project it caps rep email codes, which are the rep login path, at 2 per hour project-wide for built-in SMTP; `otp_expiry = 3600` (L237) also leaves a one-hour code lifetime. Local-only setting; flagged as something to check against the hosted project before a pilot.
