## Cross-cutting gaps
- No UI for any stock or order feature: apps/web has only login shells; rep PWA home is a placeholder. All 8 BACKEND ONLY items are unusable by a real rep or manager.
- Offline engine (P1-09) and `packages/shared` (generated types, validation, i18n en/ur) are not built, so ORD-10 and any offline stock count are server-only.
- Payments do not exist (no `payment`, allocation, installment schedule or receipt tables): blocks ORD-05 schedule/receipt numbers, ORD-03 `closed`, ORD-02 true exposure, AGT-03 pay-before-release.
- Vault (P1-05) is not built (`supplier_vault` is an empty schema): no `receipt` movement path, so no way to put purchased stock in the warehouse except an approved adjustment; INV-01 cost price and INV-10 valuation have nowhere to live.
- Lost-demand capture from orders, deliveries, bag loads and agent purchases (DEM-02/03, P1-17) is not implemented; four `demand_source` enum values (`order_shortfall`, `delivery_shortfall`, `bag_load_shortfall`, `agent_purchase_shortfall`) are never written by any function.
- Variance and low-stock outputs (INV-05, INV-06) are pull-only queries; no digest, alert or scheduled job consumes them.
- No document rendering (invoice PDF/image) and no storage for it.
- Agent track (P1-15) is entirely absent: role enum, price table, purchase, app, and no pre-order entity.
- Catalogue and stock data blocked on real product list (OQ-16 / B-10); only dummy data is allowed.
- Test coverage is database-level only (Vitest + pg); I did not run it. Playwright covers rep sign-in only. No test of any sort exercises a UI path for these requirements.

## Suspected defects
- deliveries.sql:241 and :265: the delivery source ignores `sales_order.delivery_mode`. `rep_deliver` always delivers from the rep's bag and `office_deliver` always from a warehouse, whatever the order says (`bag_now` / `warehouse`, orders.sql:21). ORD-01 makes delivery mode a chosen field; today it has no effect. A `warehouse` dispatch order can be delivered out of a rep's bag, and a `bag_now` order can be delivered by the office from the warehouse.
- orders.sql:202-207 `app.salon_exposure`: counts the full `total_paisa` of every confirmed, part-delivered and delivered installment order and never reduces it (no payments; `closed` is never reached). A salon that paid in full still looks fully exposed, so legitimate repeat installment orders will be held over_limit once real use starts. Documented as A-10 but it is a functional error against ORD-02 ("exposure + order <= limit") until payments land.
- orders.sql:168-169 / no writer of `closed`: the `delivered -> closed` transition is permitted by the guard but no function performs it, so ORD-03's last state is unreachable. Orders counted for "3 delivered orders" use `delivered`/`closed` (deliveries.sql:200) so that part is fine.
- orders.sql:350-353: `hold_credit` stores only the first failing condition (blocked > plan_not_allowed > over_limit); the manager-release code (orders.sql:505-514) re-derives each condition separately, so this is handled, but the stored `hold_credit` shown to the rep (`my_orders`) can hide a second reason.
- deliveries.sql:184-186: one invoice is issued per delivery. A part-delivered order gets several invoices, each carrying its own number; ORD-04 reads as "an invoice" per delivery so this is consistent, but the invoice shows the order's `plan` and no installment schedule (ORD-05), and the discount on each is a pro-rata recomputation (`v_sub - v_tot`), not a stored order discount. Needs a product decision before invoice rendering.
- inventory.sql:693 and :660 (foundation.sql:660): `write_off` approval requests can be created (owner-checker) but no function consumes them; `office_post_adjustment` rejects `a.kind <> 'adjustment'`, so an approved write-off cannot be posted. INV-03 write-off/damage/expiry has no path.
- orders.sql:402: only reps can create orders ("only reps take orders in Phase 1"). ORD-01 says "Create an order for a salon" without limiting to reps, and doc 06 allows the office to act on behalf; confirm intent (orders.test.ts: "needs an open day; office users do not take orders in Phase 1").
- inventory.sql:827-835 `app.low_stock`: totals warehouse plus all rep bags into one figure per SKU, so a warehouse at zero with stock sitting in bags is not flagged. INV-06 does not say which basis; confirm.
