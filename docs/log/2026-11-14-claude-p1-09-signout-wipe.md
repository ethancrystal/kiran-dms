**What / why:** A review of main (727ebb3) found two defects, both confirmed by reading the code before changing it.
Defect 1, sign-out left the previous rep's outbox readable. wipeLocalData had no caller; both rep sign-out buttons only ended the session; listItems and syncHistory fell back to the user id remembered in localStorage, so /app/outbox opened with no signal after sign-out showed the previous rep's waiting items, refusals, recent sends and salon names, with Retry and Discard. Retry and Discard took any item id and never checked whose item it was.
Fixed: (a) one sign-out for every rep page (the RepSignOut button; Today now uses it too, and the account page and the gate message already did). It wipes the queue, the history and the sealing keys, then ends the session, then drops the remembered rep. Plan task 10 says "Sign-out with unsent items asks first and lists the count; confirming wipes queue and cache; cancelling keeps them", and that is what it does: with anything unsent, waiting or refused, the first tap changes nothing and shows the count with "Sign out and discard", "Stay signed in" and a link to Waiting to send. (b) Reading the queue or the history, Retry and Discard now need the session the phone holds at that moment, and Retry and Discard also refuse an item that is not in that rep's own list. The remembered id is used only to save a new action (a rep out of signal for hours must still be able to save). (c) Nothing is wiped when the server says the account or the phone is not allowed; see the rulings.
Defect 2, the account check on /app/outbox was skipped too easily. It opened unchecked when the browser reported being offline (a devtools switch) and on any answer the queue calls passing (5xx, 408, 429), so a deactivated rep could open it.
Fixed: the request is always made. The page opens unchecked only when the request got no answer at all (status 0 from supabase-js, or a failed fetch), a session is held on this phone, and the last answer this phone had from the server for that same login was "allowed". Every answer is remembered on the phone per login (localStorage key kiran.rep.gate): a "not allowed" answer keeps the page closed on a later visit with no signal and is repeated to the rep, and the next successful check replaces it. A busy server shows "could not check" and changes nothing remembered. classifyFailure is unchanged, and a spec pins that the queue still treats 5xx, 408 and 429 as passing. The decision lives in lib/outbox/gate.ts as pure functions; the layout only asks, decides and stores.
**Rulings (what, why, cost if wrong):**
1. The count shown before sign-out is every unsent item on the phone, for any login, because the wipe removes every login's items (store.clear). Why: an earlier rep whose session ran out may have left unsent work, and it must not be lost silently either. Cost if wrong: a rep is asked about items that are not theirs.
2. When the phone cannot count (storage will not open), sign-out asks first and says why, instead of signing out silently. Restrictive reading of "never silently lose unsent work". Cost: one extra tap on a browser with no storage, where nothing could have been saved anyway.
3. If the wipe itself fails, the session is still ended, and the rep is told the phone was not cleared. Why: keeping a rep signed in on a phone being handed on is worse, and after (b) what remains can be read only with that same rep's session. Cost if wrong: sealed leftovers stay on the phone until that rep signs in again.
4. No wipe on a not-allowed answer (ended session, inactive account, unapproved or revoked phone). The plan disagrees with itself here: task 10 says "A revoked device wipes local data after rotating the id", while its Review Focus says "Device revoked or session expired mid-queue: items are held and the rep is told; nothing is discarded", and the outbox core entry (2026-11-10-claude-p1-09-outbox-core) holds items for an unapproved phone. I took the non-destructive side and built no wipe there. MJ needs to settle the revoked-phone case before the B-20 part of task 10 is built. Cost if wrong: a revoked phone keeps its sealed queue until someone signs out on it; it cannot be sent, because the database refuses the phone.
5. The gate remembers the last answer per login and opens without signal only for a login it last saw allowed, which is stricter than only remembering refusals. Why: remembering refusals alone would let a login this phone never checked open the page by signing in and going offline. Cost: a rep who signs in, sees only Today (which does not run this check) and then loses signal cannot open Waiting to send until one checked page has loaded with signal.
6. A session that has run out and cannot be renewed (no signal for longer than the token's life) is not a session for reading: the lists are hidden with "This phone cannot confirm who is signed in right now ... Nothing was removed", and the page stays closed. The task said never to read with the remembered id; this is the cost of that rule, and it is a real one for an offline app: a rep out of signal for longer than the access token lives cannot see the waiting list until signal returns. Saving still works. MJ may want the token life or this rule looked at before the offline shell (plan task 6).
7. The remembered gate answer is not cleared by sign-out. Why: clearing it would let a deactivated rep sign out, sign in and go offline to get past it.
8. Other sign-outs (office, salon, the invite page) are unchanged and do not wipe the rep outbox; after (b) nothing is readable without the same rep's session. Not decided here whether they should.
