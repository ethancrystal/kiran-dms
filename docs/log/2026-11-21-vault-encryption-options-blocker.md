**What / why:** The vault foundation snapshot (commit a6ecdc7, migration 20261121150000_vault_suppliers.sql) records name, contact_name, phone and note as plain text columns. Doc 07 line 23 requires: column encryption for identity and cost fields with a *_enc suffix, using pgsodium, with the key stored in Supabase Vault, so that even a database dump or a misconfigured policy yields ciphertext, and decryption only inside the grantee-checked functions. Doc 07 section 5 acceptance test 3 repeats it: a database dump opened without the key shows ciphertext in every *_enc column. The snapshot instead relies on layered access control: supplier_vault is not in the PostgREST exposed schemas, RLS is enabled and forced with no policies (deny by default), the only door is three vault_api SECURITY DEFINER functions gated on app.has_vault_grant() (owner or an explicitly granted manager, AAL2), the append-only access log records who read or wrote what and why, and the audit trigger redacts vault row images before they reach control.audit_event (DA-033). A full dump, a stolen backup file or a future misconfiguration defeats all of that at once, and plain text is what comes out; that is the one guarantee doc 07 line 23 exists for. Doc 07 is a fixed decision MJ owns (H-26), so the agent may not pick an approach, and the work order forbids implementing encryption this wave.

**Choices:**
(a) DEVIATION, plain text plus access control. Keep the snapshot as it is, change doc 07 (line 23 and section 5 test 3) in the same pull request that lands it, and log a DEVIATION. Cheapest to build and test; the db suite is unaffected. The cost is the dump-ciphertext guarantee: a dump or backup leak shows supplier identities in the clear, and the owner digest, not the database, becomes the leak detector.
(b) pgcrypto parity. create extension pgcrypto is available in the CI embedded Postgres (verified on this host: the @embedded-postgres windows-x64 17.9.0-beta.17 package ships pgcrypto.control and pgcrypto.dll; the same npm family serves CI on linux-x64). The identity columns become bytea *_enc; pgp_sym_encrypt and pgp_sym_decrypt run only inside the vault_api functions; the key is held server-side (Supabase Vault or an Edge Function secret, reaching the function through a server-side setting) and never enters the repository. The db suite keeps working unchanged. The honest differences from doc 07's design: no pgsodium key table or derived subkeys, key rotation is a manual owner procedure, and doc 07 line 23 needs a small amendment naming pgcrypto instead of pgsodium (MJ's change). Encrypted columns also cannot be searched directly; lookups go through the functions or hashed companion columns.
(c) Full pgsodium parity, as doc 07 is written today. Hosted Supabase projects provide pgsodium; the npm embedded Postgres does not (no pgsodium file anywhere in the dependency tree), so every db test that touches an *_enc column would fail or need skipping in CI, and H-23 forbids skipping a failing test. It needs either a custom CI image with pgsodium or a hosted-only test path, both of which are spend and environment decisions above an agent, and it delays P1-05 until that exists.
