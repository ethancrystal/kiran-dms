**Task:** P1-18 (SEC-16; D-39; spec section 3)
**What / why:** Spec section 3 says auth signup is on for the email code only and the invite page is the only page that creates a login. GoTrue has no switch that allows the code but refuses passwords: with [auth] enable_signup on, POST /auth/v1/signup with a password also creates a login, and because [auth.email] enable_confirmations is off it is signed in at once with any address it names. So a login can be created outside the invite page, and the address on a login is not proof of the mailbox.

What is built instead, in migration 20261105100000: such a login has no profile and no membership, so RLS and every app function show it nothing (swept in invitations.test.ts over every relation in the five schemas); app.redeem_invitation, app.invitation_preview and app.salon_me also require the session's signed amr claim to show an emailed code; and redeeming clears any password on the login and ends its other sessions, so a squatter who registered the invitee's address with a password first keeps no way in.

The stack test's auth guard pinned the old rule (self-signup refused with signup_disabled). It now pins the new one: a password self-signup gets a session whose my_session and salon_me are null, and which cannot redeem or invite. This changes what the test asserts because the approved rule changed (D-39); no control was loosened.
**Evidence:** supabase/config.toml comment on enable_signup; invitations.test.ts (password session refused at redeem and preview; password cleared and other sessions ended; no-profile sweep), see TASK 2026-11-05-claude-p1-18-invitations for the commands and results. The guard is CI only (e2e-stack).
**Next / needs:** MJ: turning enable_confirmations on at go-live would stop a password signup from being signed in at all; it needs a confirmation email template that carries the 6-digit code, and the gate-0 checklist would list it.
